## 1. The idea in one paragraph

Cross-bank mule rings move stolen money through three banks in seconds, and banks cannot share raw customer data because of privacy law and banking secrecy, so no single bank sees the whole cascade. Z-SPECTRA v2 keeps every raw event inside its own bank's sealed container. Inside that container, a "blind sensor" converts each event into keyed-pseudonymous behavioral features (timing, rollback counts, amount bins, and compression and entropy features over a sliding window). Only allowlisted fields cross a checked boundary into a shared mesh that holds no key and no plaintext. The mesh links the same pseudonymous account across banks into a chain, scores it with an anomaly model and a classifier, and flags the cascade at hop 2, before money is cashed out at hop 3. An LLM then writes a forensic brief from blind inputs only. The mesh sends a hold recommendation, and the owning bank's operator approves it. A live audit with planted fake PII ("canaries") and a deliberate negative control proves what did and did not cross the boundary. Everything runs on IBM LinuxONE (s390x) in containers.

## 2. Problem and demo scenario

- Banks A, B and C cannot see each other's data.
- A mule ring moves funds A to B to C to an external cash-out, with a few seconds between hops.
- Without sharing, each bank sees only one innocent-looking transfer.
- Our system links the hops using pseudonymous IDs that match across banks, and flags the chain at hop 2.

The demo scenario ("Launch heist"): a scripted three-bank cascade with known timing. Hop 1 is A to B at t0. Hop 2 is B to C at about t0 + 4 s. Hop 3 (cash-out from C) is at about t0 + 9 s. The system must raise the alert when hop 2 arrives and recommend holding the account that just received funds at hop 2, before hop 3.

## 3. Scope, non-goals and mistakes not to repeat

In scope: one fraud scenario (cross-bank mule cascades), plus abort-storm and slow-drip patterns as extra threat types.

Not in scope: other industries, real bank data, real CICS or Db2 integration, autonomous freezing of accounts (we only recommend a hold), real zero-knowledge proofs.

Mistakes from the first version that must NOT come back:
- Do not use unsalted SHA-256 for account IDs. Use keyed HMAC-SHA256.
- Do not prefix IDs with `ZK_`. Use `BID_`. We call this pseudonymization.
- Do not hardcode `plaintext_exposed_bytes: 0`. Audit counters come from real scans.
- Do not put a precomputed `hop_velocity_score` in the generator. The mesh computes hop features itself.
- Do not feed the anomaly score into a classifier trained on the same data the anomaly model saw.
- Do not claim hardware compression (DFLTCC) is used unless we measured it (section 8).
- Do not claim CPU-MF counters. Rollback telemetry is simulated.
- Do not claim "<2 ms", "99%+", "unprecedented", "mathematically guaranteed", "zero-knowledge" or "anonymous".

## 4. Trust zones and threat model

There are two zones.

Zone 1, inside each bank container (plaintext zone). Holds raw events, fake customer data, the consortium HMAC key, and a local lookup from blind ID to account. Nothing in this zone leaves except allowlisted messages.

Zone 2, shared (blind-only zone). Contains the mesh, the models, the LLM caller and the dashboard. It must never hold the consortium key or any raw field.

Honest limits we state in the final deliverables:
- Blind IDs are pseudonymous, not anonymous. All banks share one key, so a bank that already knows an account number can test whether it appears.
- Sensors read plaintext. The protection is the sealed container plus the boundary, not "AI never sees plaintext".
- Data is synthetic. Latency is measured on the same host.
- Only the owning bank can map a blind ID back to a customer.

## 5. System architecture

Services (all containers on one LinuxONE VM, one user-defined Docker network `zs-net`):

| Service | Port | Holds key? | Role |
|---|---|---|---|
| `bank-A`, `bank-B`, `bank-C` | 8001, 8002, 8003 | YES (env var) | Receives raw events, runs the sensor, validates and forwards blind messages, applies hold recommendations |
| `mesh` | 8000 | NO | Links chains, scores, alerts, calls LLM, scans traffic with the canary scanner |
| `dash` | 8080 (published) | NO | Web dashboard, "Launch heist" button, audit panel |
| `replayer` (script or one-shot container) | n/a | NO | Streams raw events to the banks |

Message flow for one event:

1. Replayer sends a raw event to the right bank: `POST /event`.
2. The bank's sensor produces a blind message. The in-path validator checks it against the allowlist. The bank sends it to `POST mesh:8000/ingest`.
3. The mesh links it to earlier hops, computes features, runs Model 1 then Model 2, and decides.
4. On an alert, the mesh builds the LLM input, validates it, calls the LLM, and sends `hold_rec` to all three banks (`POST /hold`). Only the bank that owns that blind ID acts on it.
5. The dashboard shows the blind view, the decision, the exact LLM prompt, the brief, and the audit counters.

## 6. Data definitions

### 6.1 Raw event (generator output, sent only to a bank)

```
event_id        str
ts_ms           int       simulated epoch milliseconds
bank            str       "A" | "B" | "C"   (the bank that owns src_account)
src_account     str       canonical form "<bank>:<number>", e.g. "A:000123"
dst_account     str       canonical form, e.g. "B:000987" or "EXT:cashout_17"
amount          float
tx_type         str       "TRANSFER" | "PAYMENT" | "CASHOUT"
channel         str       "APP" | "WEB" | "API"
aborted_retries_last_5s  int   simulated rollback telemetry
customer_name   str       fake name (a canary)
national_id     str       fake id (a canary)
memo            str       free text that may contain fake PII (a canary)
```

Raw events must contain NO label fields.

### 6.2 Ground truth (separate file, read only by the evaluation harness)

```
event_id, chain_id, attack_type, hop_index, is_attack, ts_ms, amount
attack_type in: NORMAL, CROSS_BANK_MULE_CASCADE, ABORT_STORM, SLOW_DRIP_STRUCTURING,
                HARD_NEG_PAYROLL_FANOUT, HARD_NEG_FAMILY_RELAY, HARD_NEG_MERCHANT_BURST,
                HARD_NEG_QUICK_RELAY
```

All `HARD_NEG_*` types count as normal for scoring. Never send ground truth to banks or to the mesh.
`ts_ms` and `amount` are evaluation-only values copied from the synthetic raw event; they support alert-timing and remaining-value measurements.

### 6.3 Canonical account and blind ID (critical)

- The canonical account string is `"<bank>:<number>"`, uppercase bank letter, zero-padded number. Every bank uses the same form.
- `blind_id(key, canonical) = "BID_" + hmac.new(key, canonical.encode("utf-8"), hashlib.sha256).hexdigest()[:12]`
- Because both sides hash the same canonical string with the same key, the `dst_bid` that Bank A emits for "B:000987" equals the `src_bid` Bank B emits when "B:000987" sends money onward. This match is how the mesh links hops across banks. Test it explicitly.

### 6.4 Wire contracts (frozen, enforced by the validator)

Bank to mesh (`POST /ingest`):
```
bank        "A" | "B" | "C"
seq         int           per-bank increasing counter
t_ms        int
src_bid     "BID_" + 12 hex chars
dst_bid     "BID_" + 12 hex chars
amt_bin     float         multiple of 0.25, = floor(4 * log10(max(amount, 1.0))) / 4
f           list of 8 floats, order = SENSOR_FEATURES in schema.py
sensor_us   float         microseconds spent inside the sensor for this event
```
No other keys are allowed. No string longer than 32 characters.

Mesh to LLM (input JSON):
```
chain       list of [bank, bid, dt_ms, amt_bin]   one entry per hop; bid = that hop's dst_bid;
                                                   dt_ms = ms since previous hop (0 for first)
p_cascade   float 0..1
anom        float 0..1   (higher means more anomalous)
evidence    list of [feature_name, percentile]    top 3 features, percentile 0..100
```

Mesh to bank (`POST /hold`, sent to ALL banks):
```
bid         "BID_..."
alert_id    str   e.g. "AL_" + 8 hex chars
```
Each bank checks its own local blind-ID index. Only the owning bank acts. Others ignore it. Holds are recommendations: the bank's operator must approve in the UI.

## 7. Component requirements

### 7.1 Generator (`gen/generator.py`)

Signature: `generate(config, seed) -> (raw_events, ground_truth, accounts_by_bank, canary_list)`

- Fully deterministic for a given seed.
- Defaults: 3 banks, 2,000 accounts per bank, about 20,000 events over a simulated 24 hours. Increase `DEMO_EVENTS` for longer runs.
- Per-bank clock offsets of up to +/-500 ms (to test clock skew).
- Normal traffic: Poisson arrivals, log-normal amounts, aborts about Poisson(0.05) per 5 s.
- Attack and hard-negative types:
  - CROSS_BANK_MULE_CASCADE: 2 to 4 hops, gaps 1 to 15 s (log-normal), amount carry-over 0.90 to 0.99 per hop with noise, occasional split into two onward transfers, aborts about Poisson(0.5) at mule accounts, ends in an EXT cash-out.
  - ABORT_STORM: 5 to 30 rollbacks within 5 s at one bank, bursty, single-bank.
  - SLOW_DRIP_STRUCTURING: 20 to 40 transfers of just-under-threshold amounts over 20 to 90 minutes to 1 to 3 destinations. This type is HELD OUT: it appears only in the test split and never in training.
  - HARD_NEG_PAYROLL_FANOUT: one source to many destinations in seconds, no onward hops.
  - HARD_NEG_FAMILY_RELAY: legit multi-bank hops with hour-long gaps.
  - HARD_NEG_MERCHANT_BURST: many small payments to one destination in seconds.
  - HARD_NEG_QUICK_RELAY: legit fast two-hop relay (escrow or exchange style) with overlapping timing and carry-over.
- Difficulty knobs in `GenConfig` (noise, overlap between cascade and quick-relay timings). Tune so the classifier is good but NOT perfect (target recall at 1% FPR around 0.80 to 0.95 on cascades). A result near 100% means the data is too easy and must be made harder.
- About 2% label noise in the ground-truth file.
- Plant canaries: `customer_name`, `national_id` and `memo` always hold fake PII, and some memos contain extra tokens like `CANARY_MEMO_xxxxxx`. The returned `canary_list` contains every fake name, national id, memo token and raw account string.
- Also output `accounts_by_bank`: for each bank, a list of `{account, customer_name}` (synthetic KYC), used only inside that bank container.

### 7.2 Blind sensor (`bank/sensor.py`)

Signature: `BlindSensor(key: bytes, bank: str, ref_window: bytes).process(raw: dict) -> dict` (a bank-to-mesh message).

Per-entity state: a sliding window of the last 32 events for each `src_account`.

Frame per event (one text line), then the window is the concatenation of up to 32 lines (roughly 0.5 to 2 KB):
`"{tx_type}|{amt_bin}|{gap_bin}|{abort_bin}|{dst_bid[:6]}\n"`
- `gap_bin` and `abort_bin` are coarse log or linear buckets defined as constants.

The 8 features, in this exact order (`SENSOR_FEATURES`):
1. `log_amount_bin`: the `amt_bin` value (never the exact amount).
2. `log1p_gap_ms`: log1p of ms since this account's previous event (cap at a documented maximum for the first event).
3. `aborts_5s`: `aborted_retries_last_5s`.
4. `tx_count_60s`: events by this account in the last 60 s.
5. `distinct_dest_60s`: distinct destinations in the last 60 s.
6. `window_ncd`: NCD between the window text x and a pinned reference text y, NCD(x,y) = (C(xy) - min(C(x),C(y))) / max(C(x),C(y)), where C is the zlib-compressed length at level 6.
7. `compression_ratio`: C(x) / len(x).
8. `window_entropy`: Shannon entropy (bits per byte) of x.

Requirements:
- The reference text y is a fixed file `bank/reference_window.txt`, generated deterministically from the normal-traffic profile, and identical in all banks. Never regenerate it at runtime.
- Measure `sensor_us` with `time.perf_counter_ns()` around the whole `process` call.
- Output must contain only allowlisted fields. The raw event never appears in logs.
- Compression runs inside the bank container, on the quantized window, never on a single hashed string.

### 7.3 Boundary audit (`audit/`)

Two layers.

Layer 1, in-path validator (`audit/validator.py`): `validate(channel, msg)` raises `BoundaryViolation` on any key not in the channel's allowlist, wrong type, out-of-range number, string over 32 characters, `BID_` pattern mismatch, or wrong feature-list length. Every outbound send (bank to mesh, mesh to LLM, mesh to bank) must call it. No send path may bypass it.

Layer 2, canary scanner (`audit/scanner.py`): `CanaryScanner(canary_list).scan(channel, text) -> hits`. Scans every message received by the mesh, every log line (via a logging handler) in banks and mesh, and every LLM prompt and response. The canary list is a test instrument supplied by the harness (file mounted into the mesh container) and is never used for decisions.

Counters (real, never hardcoded): production messages scanned, bytes scanned, canary hits, messages blocked by the validator. Negative-control scans and hits are kept in separate self-test counters and do not increment production canary-hit status.

Negative control: a test-only function (and dashboard button) that deliberately builds a message containing a canary and sends it through the scanner path. It must be CAUGHT. The audit panel shows "negative control: caught". If it is not caught, the audit is broken.

The in-path validator and scanner results go to `audit.log`, and that log is itself scanned.

### 7.4 Bank service (`bank/service.py`)

Flask app. Endpoints:
- `POST /event`: raw event in, run sensor, validate, forward to mesh.
- `POST /hold`: receive `hold_rec`. If `bid` is in the local index, mark it "hold recommended, awaiting operator". Otherwise ignore silently.
- `GET /reveal?bid=...`: operator console only. Returns the fake customer name if the BID is local. Never called by the mesh or LLM.
- `GET /health`.

At startup the bank loads its synthetic accounts file and builds a local index `BID -> account`. The key comes only from the env var `CONSORTIUM_KEY` and must never be logged or returned.

### 7.5 Mesh (`mesh/`)

Hop linking (`mesh/chain.py`):
- Keep recent events in memory, indexed by `dst_bid`.
- For an incoming event with `src_bid = S` at time t: look for a prior event with `dst_bid == S` where `-2000 <= t - t_prev <= 60000` ms (the negative tolerance handles clock skew; clip dt to 0 for features). If several match, take the most recent. The new event inherits the parent's chain and has `hop_depth = parent.hop_depth + 1`. Otherwise it starts a new chain with `hop_depth = 1`.
- The mesh assigns its own chain ids. It never sees ground-truth chain ids.

Mesh features (`MESH_FEATURES`, computed by the mesh): `hop_depth`, `dt_prev_hop_ms` (0 if none), `amount_carry_over` (difference of the two amt_bin values, 0 if none), `banks_in_chain`, `chain_span_ms`.

Scoring (event level): the model input is the 8 sensor features plus the 5 mesh features (13 values). Model 1 produces `anom`. Model 2 takes the 13 features plus `anom`.

Alerting:
- Cascade alert: `hop_depth >= 2` and `p_cascade >= T_cascade`. One active alert per chain. This is "flagged at hop 2". If a hop-one unknown-anomaly alert exists, promote that alert when the cascade condition is met. The hold target is the `dst_bid` of the event that raised the cascade alert (the account that just received funds).
- Unknown-anomaly alert: `anom >= T_anom` with label "UNKNOWN_ANOMALY" (this is how the held-out slow-drip type is caught by Model 1 alone).
- Thresholds are set at 1% false positives on normal validation events and stored in `models/thresholds.json`.

Evidence: top 3 features by percentile of the event's value against the normal training distribution (stored with the models). No SHAP needed.

Endpoints: `POST /ingest`, `GET /state`, `GET /stream` (server-sent events), `POST /reset`, `GET /health`.

### 7.6 Models and training protocol (`mesh/models.py`, `train.py`)

- Model 1: scikit-learn `IsolationForest` (about 100 trees, fixed seed), trained on NORMAL events only (including hard negatives) in split A.
- Model 2: scikit-learn `HistGradientBoostingClassifier` (fallback allowed by default; Snap ML only if installed and working), trained on split B. Classes: NORMAL, CROSS_BANK_MULE_CASCADE, ABORT_STORM.
- Splits are time-based and grouped by chain: split A (earliest 40%), split B (next 30%, with a validation slice used only for thresholds), test (last 30%). All events of one ground-truth chain go to the same split. SLOW_DRIP_STRUCTURING appears only in the test split.
- Train on the target LinuxONE VM (s390x), OR verify that a model saved on x86 loads and predicts identically on s390x. Cross-endianness pickles are a known risk. Do not assume they load.
- All randomness is seeded.

### 7.7 LLM brief (`mesh/llm.py`)

- Input is exactly the mesh-to-LLM JSON (6.4), validated before sending, and passed through the scanner.
- System prompt: the model only knows blind IDs and numbers, must never guess identities, must not invent facts, and must return JSON: `summary`, `suspected_pattern`, `risk_level`, `recommended_action`, `limits`.
- The exact prompt JSON is stored and shown on the dashboard.
- Mode order of preference: (1) the method taught in the LinuxONE lab 2 or a small local model on the VM, using its supported API, (2) an API call carrying only the blind payload (API key only in an env var, never shown on screen), (3) a deterministic template. The llama.cpp adapter uses `POST /v1/chat/completions` with `model`, `messages`, and JSON response format. The response always carries `llm_mode` = `local` | `api` | `template`, and the dashboard shows it. A template must be labeled as a template.
- Configure the endpoint with `LLM_URL`, the loaded model with `LLM_MODEL`, and optional credentials with `LLM_API_KEY`. The user message must be byte-for-byte the compact validated blind JSON displayed as the prompt. Use `max_tokens=150`, `temperature=0.2`, and a 60-second request deadline; on failure or timeout, show the deterministic template. The dashboard shows the alert as soon as it is raised and updates the brief when it arrives.
- The LLM response is also scanned for canaries.

### 7.8 Dashboard (`dash/`)

Flask plus plain HTML and JavaScript. No build step, no Streamlit. Panels:
1. Left, "What crosses the boundary": live stream of blind messages (blind IDs, bins, feature vectors) and the audit counters.
2. Right, "Decision": chain visualization, `p_cascade`, `anom`, evidence, hop at which the alert fired, and the LLM brief with `llm_mode`.
3. "Exact LLM prompt": the literal JSON that was sent.
4. "Audit": scan counters, canary hits (expected 0), and a "Run negative control" button that must show "caught".
5. "Platform evidence": output of `lscpu` (Architecture, Byte Order, Model name, Flags), `/proc/sysinfo` lines, and `docker ps`, fetched live.
6. "Launch heist" button and a "Reset" button.
7. Benchmark numbers shown in the UI are read from `results.json` only.
8. Optional if time allows: "Bank operator" tab that calls `GET /reveal` on the owning bank and shows the hold approval.

### 7.9 Replayer and heist script (`tools/`)

- `replayer.py`: reads generator output and posts each raw event to its bank, preserving relative timing with a speed factor.
- `heist.py`: posts the scripted three-bank cascade from section 2, using fresh accounts, so the demo is repeatable.

## 8. LinuxONE (s390x) requirements

- The platform is s390x, which is big-endian. Never assume byte order. Always give an explicit byte order if you use `struct` or raw numpy buffers. Use JSON on the wire, never pickle across services.
- Build Docker images ON the LinuxONE VM. Use a base image that has an s390x variant (verify with `docker pull`).
- Before a target run, execute `python3 tools/linuxone_preflight.py` to record Python imports and Docker CLI/daemon availability. Use `--install-check` to try installing the project requirements into a temporary directory. Do not treat a host package check as proof that all Docker images build.
- Keep each container small. Assume the VM has limited RAM (check with `free -h`). Keep models small.
- Platform proof commands to run and screenshot:
  - `lscpu | grep -E 'Architecture|Byte Order|Model name|Flags'`
  - `grep -m1 features /proc/cpuinfo` (look for `dflt`)
  - `grep -E 'Manufacturer|Type|LPAR|VM00' /proc/sysinfo`
  - `docker ps`
- Hardware compression claim rule: only claim DFLTCC use if (a) the `dflt` flag is present AND (b) the benchmark shows a measurable difference with the hardware toggle on versus off. Otherwise say only that the flag is present, or say nothing. The toggle mechanism (an environment variable the installed zlib documents) is a config value `HW_TOGGLE_ENV` filled in after checking, not assumed.
- `bench/zlib_bench.py` compresses buffers of 1 KB, 16 KB, 256 KB, 4 MB and 64 MB at level 6, with the toggle on and off, and records microseconds per call and `zlib.ZLIB_RUNTIME_VERSION`.
- Containers must show isolation: `docker exec mesh env` and `docker exec dash env` must not contain the consortium key. There is a test for this.

## 12. Testing and definition of done per segment

Everything below runs with `pytest -q` and must pass on both a laptop and the VM.

- S2 Generator: same seed gives identical output; raw events contain no label fields; canaries appear only in raw events and the canary list; slow-drip appears only in the test split; cascades have the specified hop structure.
- S3 Sensor: same input and key give the same blind ID; a different key gives a different ID; `dst_bid` from bank A equals `src_bid` from bank B for the same canonical account; output has only allowlisted fields; 8 features in the right order; feature values are finite.
- S4 Audit: validator rejects an extra key, a long string, and a bad `BID_` pattern; scanner finds a planted canary; negative control is caught; counters are computed, not constants.
- S5 Containers: three banks and the mesh start from `run.sh start`; `/health` is green; the mesh and dash containers contain no key; `run.sh reset` returns a clean state.
- S6 Mesh and models: links a two-hop chain across banks within the time tolerance; handles clock skew; thresholds are loaded from `thresholds.json`; the scripted heist raises one alert at hop 2; the hold recommendation reaches the owning bank only.
- S7 LLM: prompt validates against the contract; `llm_mode` is always set; the template fallback is labeled.
- S8 Dashboard: every panel loads; benchmark numbers come from `results.json`; the negative-control button shows "caught".
- S9 Evaluation: `results.json` is produced and matches the schema; the clean-clone run reproduces the numbers within the reported spread.

Each segment's README section must contain one demo command.

## 13. Build order and fallbacks

Order: contracts and repo (S1), platform proof (S0), then generator, sensor and audit in parallel (S2, S3, S4), then a one-process walking skeleton (event to sensor to validator to mesh to alert), then containers (S5), mesh and models (S6) and the LLM (S7) in parallel, then the dashboard (S8), evaluation (S9), packaging (S10).

Fallbacks:
- No Docker or Podman: use process mode with separate service environments and loopback ports. The demo runs under the invoking OS account, so this fallback is not equivalent to container or separate-user isolation.
- zlib hardware toggle is unset: do not claim DFLTCC use. Report the host flag and measured zlib results only when results exist; `hw_on_us` remains unavailable until a documented toggle is configured.
- Compression adds no lift: lead with the privacy boundary and audit, and report the result honestly.
- Snap ML will not import: use scikit-learn HistGradientBoosting.
- No LLM on the VM: lab 2 method, then a compatible API call with the blind payload only, then a labeled template.
- Short on time: drop to 2 banks, reduce the ablation to two configurations, 3 seeds, and skip the slow-drip holdout.
